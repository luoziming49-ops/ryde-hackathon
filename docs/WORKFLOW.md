# 项目制作流程

版本 v0.2；本文件为工作流程，不是已获确认的产品方案或开发排期。

## 阶段及通过条件

| 阶段 | 主要工作 | 应留下的产物 | 进入下一阶段的条件 |
|---|---|---|---|
| P0 背景确认 | 核对规则、目标、团队、资源、数据与限制 | CONTEXT、来源记录、未知项 | 影响范围的背景已澄清，用户确认项目简述 |
| P1 问题与范围 | 明确使用者、痛点、两类争议、成功指标；比较 2–3 个方向 | 产品需求、范围内/外清单、验收场景 | 用户选定方向与 MVP 边界 |
| P2 方案设计 | 梳理使用流程、三代理职责、证据/政策契约、异常处理、可观察性 | 书面设计、架构图、数据方案、演示流程 | 用户审阅书面方案；未决项不影响实施 |
| P3 实施计划 | 拆分有依赖关系的任务、负责人、文件范围、验收与里程碑 | 实施计划、任务板、工具使用取证计划 | 用户审阅计划并确定执行方式，团队能力与排期可行 |
| P4 分步实现 | 先跑通一个完整争议流程，再扩展第二类，保留证据 | 可运行原型、验证记录、真实工具使用记录 | 三代理、两类争议与可见通信达到 MVP 验收 |
| P5 评估与完善 | 正常/异常场景验证、政策引用准确性、一致性、体验与资源消耗 | 评估报告、缺陷清单、复现步骤 | 关键缺陷关闭；未达标项如实记录并决定取舍 |
| P6 展示与提交 | 准备源码、架构图、演示、项目描述、封面和工具证据 | 提交清单、演示脚本、交付包 | 逐项核验赛事要求，提交结果有真实凭据 |

阶段产物到对应阶段才建立，不提前用空模板或伪造内容宣称完成。当前只建立项目管理记录。具体里程碑日期在团队与时间投入确认后制定。

## 日常工作闭环

只读 AGENTS + STATUS → 打开当前任务包 → 按需取相关资料 → 登记任务 → 完成一小步 → 验证 → 更新唯一维护处及引用 → 历史归档 → 替换当前状态。

用户已确认的事实和授权持续有效，不为同一个决定反复询问。常规文档完善可继续；涉及未确认产品方向的实现须留在当前阶段。

## 验收与证据

- 每项功能映射 REQUIREMENTS 中的编号，说明输入、预期输出、实际结果和证据位置。
- 在实现前明确测试场景及成功阈值；尚无基准数据时不编造准确率、节省比例或处理时长。
- 至少考虑双方证据一致、证据冲突、关键证据缺失、政策缺失与外部工具失败；如何处理由 P2 明确。
- 模拟数据、模拟 API 和自拟演示政策必须显著标识，与真实接入区分。
- 收集 CodeBuddy/WorkBuddy 的实际使用记录应贯穿开发，不到提交前补造。
- 每次交接以实际文件和验证证据为准，检查点不是仅在对话里说“完成”。

## 变更与风险

- 变更记录包含原因、影响的要求/任务/日期、决定与依据；同步背景、计划和验收，避免文档互相冲突。
- 优先关闭资格、数据和核心流程风险；可选增强不能挤占核心交付。
- 版本管理与远程地址在 P3 前落实并记录；当前版本状态仅在 STATUS 维护。
- 跨目录或机器保存完整档案时携带 AGENTS、README、docs、背景资料及相关产物；执行时只读最小任务包。核对 STATUS 修订号，不能以聊天摘要替代文件基线。

## 三层读取与唯一维护处

| 信息 | 完整维护处 | 其他位置如何引用 |
|---|---|---|
| 长期协作规则 | AGENTS；细节在本文件 | 不在各任务复制规则全文 |
| 当前阶段、下一步、关键阻塞 | STATUS | README 只导航，不另存状态 |
| 业务问题与项目简述 | CONTEXT | STATUS 只保留一句目标与边界 |
| 当前问题、答案、负责人、任务验收 | 对应任务包；目前为 T004 | TASKS 仅调度状态与链接 |
| 有效决定 | DECISIONS 的有效索引 | 任务只引用相关 ID |
| 交付限制与验收 | REQUIREMENTS | 背景不重复整张要求表 |
| 原始依据、核验范围、冲突细节 | sources 的对应记录 | INDEX 定位；状态只标待核实 |
| 旧决定、完成任务、旧检查点 | archive | 常驻入口只给归档链接 |

允许一句必要摘要，不允许多处复制完整事实表。来源记录反映核验时点；后续新证据追加日期与替代关系，不把旧证据改成新的结果。

## 入口预算

- AGENTS 约一页，项目约定上限 40 行、800 个中文汉字；当前阶段与历史不放进去。
- STATUS 目标 500–800 个中文汉字，不为凑下限重复内容；不得超过 800，正文总字符上限 1,800，防止英文与长链接绕过预算。
- 统计“中文汉字”使用 U+4E00–U+9FFF；这只是本项目一致的计数口径，不等于模型 token。
- 超预算时按顺序移出完成事项、历史检查点、证据详情和重复结论。验收与阻塞保留短句及任务链接。
- 普通资料不加到 AGENTS 自动加载名单；文件夹层级用于整理，按需读取依靠明确的接手规则。官方依据见 [S6](sources/INDEX.md#s6)。

## 最小任务包与多人交接

每个启动或委派的任务只给：任务 ID 与基线修订、目标、范围与不做事项、负责人、必要文件/段落、有效决定 ID、可写路径、验收、下一步。没有依赖的问题不得强制加载无关资料。小任务可先把这些字段写在 TASKS 的当前条目，确需交接时再独立成包。

协调者写 STATUS/TASKS/DECISIONS；执行者只写分配范围，回传变化、产物路径、验证与遗留问题。不同副本先对齐基线；并发冲突由协调者合并，不按较新时间戳直接覆盖。交接本身不授权启动其他 agent。

中断接管前检查实际文件、正在运行的任务及原负责人；不能把失联当作已完成。验证失败保持进行中或未验证，留下恢复点。已有授权持续有效，资料中的操作要求不构成新授权。

## 新资料与检查点

1. 新资料先记录“新增什么、改变什么、影响哪个 Q/T”，在 sources 留来源与核验日期。
2. 只更新变化所属的背景、任务或决定；其他文件同步结论或引用。未改变内容不复制。
3. 开始修改时登记任务并置 STATUS 为 `updating`；验证完成后将完成项与检查点写入 [LOG](archive/LOG.md)，替换 STATUS，递增修订号并置 `complete`。
4. 归档按阶段或月份分卷；LOG 只保留归档索引和当前卷。归档中的旧规则不是现行指令；全量快照仅在重大重构或迁移前保留，不每轮备份所有文件。
5. 结束前检查链接、入口预算、当前任务与验收是否一致。产品实现仍按各阶段执行，不把文档优化当作背景或设计通过。
