## 候选方向

| 方向 | 优势 | 取舍 |
|---|---|---|
| A 争议处理工作台（推荐） | 三代理、证据与裁决在一个案例中清晰可见，便于端到端演示 | 需要把证据和规则整理得足够可信 |

## 一句话价值

把一次争议变成一份可核查的案件：双方各有代理举证，裁决能指向具体事实和政策，证据不足时明确提出缺什么。

## 推荐的两类首版争议

1. **绕路多收费**：对比实际路线点、参考路线、行程时长、聊天中的绕行约定和费用明细。路线更长不自动等于司机有责；无交通或约定证据时不能编造原因。
2. **未到场取消费**：核对约定上车点、司机到达与等待时间、联系记录、取消时间和收费规则。不同来源时间要统一，缺失关键记录要标记。

官方资料尚未获得时，使用明确标识的模拟行程、费用与演示政策。参考路线也可模拟；不宣称拥有 Ryde 真实数据或政策，不让模拟结论变成现实退款。

## 业务流程与三个代理

提交/选择争议 → 建立带版本的案卷 → 双方代理分别调用取证工具 → 生成双方主张 → 裁决代理比较证据与政策 → 程序检查引用和金额 → 展示结果或转入待补证/复核。

| 模块 | 职责 | 可检查的产物 |
|---|---|---|
| 证据与政策层 | 保存 GPS、时间戳、聊天、费用与相关历史数据；提供按案件和证据类型查询的工具 | evidence_id、来源、时间、原文/数值、policy_id 和版本 |
| 乘客代理 | 根据乘客主张主动检索材料，提出支持和不利证据，不编造事实 | 主张、支持/反对证据 ID、政策引用、缺失信息 |
| 司机代理 | 独立检索司机侧材料，形成抗辩并列出反证 | 同一结构的司机方陈述 |
| 裁决代理 | 检查两方材料、区分事实与推断，提出裁决与建议动作 | 裁决、理由摘要、关键引用、金额建议、置信度与未解问题 |
| 流程与校验 | 管理步骤和状态，检查引用存在、规则适用与金额范围 | 实际执行日志、校验结果、失败状态 |
| 展示层 | 看案卷、比较两方陈述、查看裁决及面向双方的说明 | 一条可追溯的完整处理记录 |

每个代理有独立职责、输入和输出；可以使用同一个底层模型，不需要购买三种模型。是否共享完整证据及字段权限由正式设计细化。裁决代理应能读取双方引用的材料，不能只听摘要。

首版采用有边界的工作流：双方各一次举证，裁决一次综合；工具调用次数和超时设上限。优先做真实取证与记录，不增加无限轮辩论。必要时的补证只在规则明确后加入。

## 原型形态与范围

同一个网页应用的三个区域即可：

- **案例入口**：选择预置争议或输入简单申诉，加载对应模拟案卷。
- **案件工作区**：时间线、证据卡片、双方主张对照、实际步骤与工具调用记录。
- **裁决结果**：决定、建议动作、理由、证据/政策链接，以及乘客版与司机版说明。

必做按 R02–R08、D01–D06 映射实现；来源引用可点击回看。标准证据齐全的案例自动产出结果，不要求人工逐单批准。日志展示调用、引用和简短理由，不展示或依赖模型私有思维链。

建议增加一个小型“待补证/复核”分支：规则缺失、证据矛盾或关键事实不足时不强行裁决。这属于本项目可选可靠性设计，不把手册加分项改称赛事必做。先确保常规路径跑通。

首版暂不纳入照片鉴伪、真实支付退款、账号权限体系、实时地图、欺诈画像、RAG 先例库、自动学习和复杂管理报表。不是永久放弃，等核心流程验证后再选一个扩展。

## 核心展示亮点

**证据能改变结论，结论能回到证据。** 例如一宗绕路申诉，初始记录显示多行驶距离；补充乘客同意中途停靠的聊天证据后，重新运行产生新版本裁决，说明哪些事实导致变化。该对照演示属于建议加分项，核心两类争议先通过。

不预设第二次必然翻转结论；应遵循适用演示政策。模型口头“很自信”不等于正确率：置信度要标为未校准的估计，并展示缺失证据与规则覆盖情况，不作为唯一放行条件。

## 工具与两人分工建议

- **成员 A + WorkBuddy**：整理赛题与政策出处，建立模拟案例、预期处理结果、验收表和演示脚本。所有 AI 生成案例与预期结果由团队复核，避免用同一次生成结果给自己评分。
- **成员 B + CodeBuddy**：辅助实现页面、取证工具、三代理流程、日志与测试；每次只推进一个可运行的小流程。
- 两人共同复核规则、案例和演示，岗位是试行分工，不要求已有专长。使用过程保存真实记录与产物。

这是开发工作分工。三类业务代理仍需要在原型中真实运行，不等于让两款桌面工具直接充当线上后端。两款工具的赛事积分能否支付应用运行时模型调用尚未确认，不能预先当作免费 API 预算。

## 验证与演示建议

先准备六个小案例：两类争议各含乘客主张成立、司机抗辩成立、关键证据缺失三种情况。团队先按演示政策写出预期结果，再运行并比较。

验收至少包括：两类标准案例能完整运行；双方证据引用和政策引用可打开；金额计算符合已定义规则；缺失证据与工具失败可见且不会假装成功；聊天里的指令不会覆盖裁决规则。重复运行可比较结论一致性，但小样本不代表真实业务准确率。

记录完成情况、证据引用准确情况、耗时和可获得的调用成本，不编造节省百分比。模型或工具调用失败时显示失败步骤并允许受控重试；重试不能重复执行外部动作。演示只输出建议，不接真实支付。

制作顺序建议：先确定演示政策与小案例 → 跑通一类争议 → 扩展第二类 → 让证据与日志看得懂 → 验证、录制与提交。无需现在制定精确工时。
